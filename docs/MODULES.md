# Modules

`src/Plugin.cs` (`DiscoverModules()`) reflects over the assembly at `Awake` and instantiates every
non-abstract subclass of `FeatureModule` (`src/FeatureModule.cs`) it finds — there is no registry
to edit; dropping a new file with such a class is enough. There are exactly 35 such classes. Each
module owns its own Harmony instance, binds its own config section, and declares a `Side` (Server /
Client / Both) — a module whose side doesn't match the running half (dedicated server vs. player
client) is never configured or patched, and shows `disabled(side)` in `nvlb.status`. The table below
adds a 36th row, `Tiers`, for the one piece of shared config that isn't a `FeatureModule` at all
(see the note after the table).

**Enabled-toggle restart rule** (same mechanism for every module — see `FeatureModule.TryEnable` /
`Configure`): `TryEnable()` calls `ApplyPatches()` — which installs the module's Harmony patches —
exactly once, at plugin `Awake`, and only if the module started up `Enabled`. Flipping `[Section]
Enabled` **off** at runtime works live: the Harmony patches stay installed, but every patch body
gates on `Active` (`Applied && Enabled`), so behaviour turns off immediately. Flipping it **on** at
runtime when it started off does **not** take effect until the game/server restarts, because
`ApplyPatches()` is never called again. This is stated once here rather than in every row; the
"Restart for Enabled toggle" column just says `on: restart / off: live` throughout — no module
overrides it (checked: `ExtraSlotsModule`, `VanguardShadowModule`, `DualPowersModule` and
`FistsAndShieldsModule` all do extra cleanup work in `OnConfigChanged`/`Disable` when turned off,
e.g. evacuating stranded items, removing a status effect or restoring the item types they changed,
but none of them re-install patches, so the rule still holds).

**Hot-reload**: `Config.Reload()` (via `ConfigWatcher`, on file-change or a server's `ServerSync`
push) fires `SettingChanged` for every entry bound through `BindSynced`/`BindLocal`, which every
module wires to its own `OnConfigChanged`. In practice this means "yes" for essentially every
setting below — the module re-reads it on the very next use. The table calls out the few modules
where a changed value is visibly deferred (e.g. `ServerKeysModule`, whose keys are re-applied to
the live `ZoneSystem` immediately only if `ApplyOnLoad` is true) or where the setting only gates a
diagnostic that runs once per world load.

**The tweak door** (`src/Access/TweakDoor.cs`, module `Access`): a client sends
`NVLB_Tweak(section, key, value)` over `ZRoutedRpc`; the server checks `[Access] TweakAccess`, the
per-setting tier against `adminlist.txt` (`ZNet.IsAdmin`), that the setting is known and live,
parses and validates the value against the catalog's range/choices, rate-limits the sender, then
writes the cfg file on disk with a timestamped `.bak-YYYYMMDD-HHMMSS` backup in exactly cfg.py's
format and sets the entry in memory — so the existing watcher to `Config.Reload()` to
`SettingChanged` to ServerSync path pushes it to everyone. The cfg file stays the single source of
truth, so `cfg.py` and the backups keep working unchanged. A 20-deep-per-key undo history backs
`NVLB_Undo`; `NVLB_ResetModule` puts one section back to defaults under one backup. Local
(`BindLocal`) settings never go to the server — the tab writes the client's own cfg.

**The Network panel** (`src/Access/SmoothServerBridge.cs`, 0.7.1): since 0.7.1 a tweak may target a
*second* cfg file — SmoothServer's `Nosferatu.SmoothServer.cfg`, in the same BepInEx config
directory. Those requests arrive with the section prefixed (`SS:Profiles`) and are resolved against
a hand-written **allowlist** of five (section, key, type, permitted values, tier) rather than
against the `ConfigCatalog`; everything after that — permission, tier, validation, rate limit,
backup, line-level file write, undo, audit, announce — is the same code, and the audit line names
the row by its label (`[NVLB] Erik set Network preset FastLink -> Default`). A SmoothServer key that
is not on the allowlist is refused however it is asked for, including by an admin, so the panel can
never reach that mod's other ~55 settings. SmoothServer is found at **runtime** through
`BepInEx.Bootstrap.Chainloader.PluginInfos` by GUID and read through its live `ConfigEntry`s — there
is no compile-time reference and no dependency; without it the panel does not exist and the door
answers "SmoothServer is not installed on this server". Setting its entry is what makes the change
instant: SmoothServer's own `SettingChanged` handlers run (a profile flip re-applies its preset
table and logs it) and its own ServerSync pushes to every client. Two extra refusals keep the
answers honest: a key that SmoothServer's preset owns cannot be moved away from what the preset
dictates (set the preset to `Custom` first), and a SmoothServer module that booted disabled is
answered "Needs a server restart", read from its own module list. `[Access] NetworkSelfTest` drives
the whole path headlessly at world load.

**Setting metadata**: every setting bound through `BindSynced`/`BindLocal` (`src/Config/Opt.cs`)
can carry a Hint (12 words or fewer, plain language, shown under the row in the settings tab), a
Range (min/max/step) or Choices for pick-one strings, a Tier (`Everyone` default, `Admin` for every
`[ServerKeys]` key, `[General] EnforceClientMod`/`Mode`/`HotReload`, `[Debug] AllowTestCommands`,
every `SelfTest`/`DryRun` and every `[Access]` key) and Live (false where a value is only read once
at boot); `FeatureModule` also carries a Theme (which group the settings tab lists it under) and a
one-line Hint. These feed a `ConfigCatalog` (`src/Config/ConfigCatalog.cs`) that the settings tab,
the tweak door's validation and the `nvlb.catalog` console command (alongside `nvlb.status`) all
read, so the three agree; a dedicated server also writes the whole catalog to `nvlb-catalog.tsv`
next to its cfg at boot. Ranges are **not** passed to BepInEx as `AcceptableValueRange` on purpose —
BepInEx clamps to an acceptable range on load, which would silently rewrite an existing server cfg;
the range is advisory for the UI and enforced only by the door, where a refusal is visible.
